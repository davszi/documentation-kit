# Migrate to kit 4.0.0

This guide applies the [4.0.0 release notes](../releases.md#400--finished-working-documents-neutral-theme-names-and-group-colours)
to an existing 3.2.1 consumer. 3.2.1 needed no migration step, so a 3.2.0
consumer follows it too. Prepare the upgrade as in the
[1.1.0 guide](1.1.0.md#prepare-the-deliverable): record the old and new kit
commits, keep a baseline build and follow the project's permissions and staging
workflow.

A project on an older version follows the earlier guides first, oldest first,
for their content steps, and then this one. It still moves its pin once,
straight to `v4.0.0`; it does not pin each release in between.

4.0.0 is a major release for one reason: a section anchor of
`rules/records.md` is removed, and lint fails on a link to it. Apart from the
pin itself, that is the only edit to existing project files that a check
enforces. The theme renames need edits that no check finds. The other steps apply rules that changed; no check enforces them, and
most need the person who owns the project to decide or approve. After the
steps below, run the [project conformance check](../../../../rules/conformance.md)
and report its findings.

| Step | Who needs it | Enforced by |
|---|---|---|
| [Move the pin](#move-the-pin) | Every project | Lint (pin check) |
| [Repoint links to the removed section](#repoint-links-to-the-removed-section) | A project that links `records.md#evidence-identity-and-frozen-records` | Lint |
| [Rename theme variables and classes](#rename-theme-variables-and-classes) | A project that uses `--adp`, `--ada` or one of seven classes | Nothing |
| [Colour navigation groups](#colour-navigation-groups) | A project with a group named `method`, `road`, `racing`, `sim` or `related work`, or one that wants fixed group colours | The build checks the table once it exists |
| [Label plot toggle chips](#label-plot-toggle-chips) | A project whose pages load `plot-toggles` with one of nine group keys | Nothing |
| [Remove references to the pin button](#remove-references-to-the-pin-button) | A project whose CSS or tests name `reader-drawer-pin` | Nothing |
| [Replace tests that import the kit's tooling](#replace-tests-that-import-the-kits-tooling) | A project test that imports a module from `.docs-kit/tooling` | Nothing |
| [Review what changed without an edit](#review-what-changed-without-an-edit) | Every project | Nothing |
| [Apply the changed rules](#apply-the-changed-rules) | Every project, decided by its owner | Nothing |
| [Reread pages that explain changed guides](#reread-pages-that-explain-changed-guides) | A project whose pages link the changed guides | Lint notes for its own records only |

## Move the pin

1. Fetch the tag and check it out:

   ```bash
   git -C .docs-kit fetch --tags origin
   git -C .docs-kit checkout v4.0.0
   ```

   `requirements.txt` is unchanged since 3.2.1, so the documentation
   environment needs no reinstall.
2. In a fresh clone or worktree whose recorded pin cannot be fetched,
   `git submodule update --init` stops with `not our ref`. In the case a
   consumer reported, it still left a clone of the kit in `.docs-kit`, and the
   two commands above worked in it. When the
   submodule's `origin` is a local path that has moved, correct the URL in
   `.gitmodules` and run `git submodule sync` first.
3. Rebuild and run lint with the project's documentation interpreter, written
   `python` here:

   ```bash
   python .docs-kit/docsite.py build --project .
   python .docs-kit/docsite.py lint --project . --strict
   ```

   The documentation interpreter is the Python 3.12 environment that has
   `.docs-kit/requirements.txt` installed. The project's context file names
   it; a checkout set up as the kit README says has it at
   `.build/docs-env/bin/python`, but a fresh clone or worktree, and a project
   that set up its environment elsewhere, may not. Check a candidate with
   `<python> -c "import mistune, pygments"`; without one, create it:

   ```bash
   python3.12 -m venv .build/docs-env
   .build/docs-env/bin/python -m pip install -r .docs-kit/requirements.txt
   ```

Done when `git -C .docs-kit describe --tags` prints `v4.0.0`. Lint fails while
the pinned commit is on none of the kit's remote branches; a tag alone does not
count.

## Repoint links to the removed section

`rules/records.md` no longer has the section "Evidence identity and frozen
records". [Finished working documents](../../../../rules/records.md#finished-working-documents)
replaces it with the opposite rule: a finished plan, decision record, review
or coordination note is deleted, not kept as an unedited copy. No other anchor
under `rules/` changed.

If the person has already approved deleting a document that holds such a link,
as the step [finished working documents](#finished-working-documents) below
describes, delete it first. Otherwise find the links:

```bash
grep -rn 'evidence-identity-and-frozen-records' --exclude-dir=.docs-kit --exclude-dir=.build .
```

The search covers HTML too. Lint checks only Markdown links, and reports each
one as `anchor #evidence-identity-and-frozen-records not found in …`. A link
written as an HTML `<a href>` fails no check and still needs the same change.

Repoint each link by what it is about:

- Keeping, citing or deleting an old document:
  `.docs-kit/rules/records.md#finished-working-documents`.
- What an experiment keeps, or when a source pin or a recorded hash stands for
  code or a document: `.docs-kit/rules/records.md#numbers-and-staleness`.
- The location manifest and the path and evidence adapters:
  `.docs-kit/rules/site/resources.md#resource-closure-and-evidence`.

A sentence that states the old rule, such as "frozen records are kept
byte-exact", is now wrong. Correct the sentence as well as the link, or route
it to [finished working documents](#finished-working-documents) below.

Three kinds of file are not edited this way:

- **An old worklog entry.** Worklog entries are never rewritten. Set
  `worklog_links_checked_from = "YYYY-MM-DD"` in `docs/site/site.toml`, above
  the first `[[nav]]` table, to the date of the first entry that lint should
  still check. Lint then skips links in older entries; text above the first
  dated heading is always checked. This also stops lint from finding other
  broken links in those entries, so choose the date with the owner. The
  build applies the same date to a worklog that is also a
  [registered source page](../../../../rules/site/authoring.md#registered-source-pages);
  see [what changed without an edit](#review-what-changed-without-an-edit).
- **A historical experiment record or another record that is not edited
  afterwards.** Report the link to the owner. A link to the section at the
  `v3.2.1` tag,
  `https://github.com/davszi/documentation-kit/blob/v3.2.1/rules/records.md#evidence-identity-and-frozen-records`,
  keeps its meaning, and the kit's own release notes use it; changing the
  record is the owner's decision.
- **A page whose words the project locks by hash.** Repointing a link changes
  its content. Get the content revision approved under the project's own
  rules before the edit, and update the lock with it.

Done when the search above lists only files the owner decided to leave, and
lint passes.

## Rename theme variables and classes

The theme no longer uses one project's names. Two CSS variables and seven
class names are renamed; the styling is the same.

| Old | New |
|---|---|
| `--adp` | `--accent` |
| `--ada` | `--secondary` |
| `badge adp` | `badge accent` |
| `badge ada` | `badge secondary` |
| `card ada` | `card secondary` |
| `band-adp` (SVG) | `band-accent` |
| `band-ada` (SVG) | `band-secondary` |
| `b-adp` (SVG) | `b-accent` |
| `b-ada` (SVG) | `b-secondary` |

A project that still uses an old name gets no error. The element only loses
its theme style, and a project rule that sets `--adp` or `--ada` no longer
changes any theme colour.

1. Search the project's own files:

   ```bash
   grep -rnE --exclude-dir=.docs-kit --exclude-dir=.build --exclude-dir=.git -e '--ad[ap]\b|\.ad[ap]\b|class="[^"]*\bad[ap]\b|\bband-ad[ap]\b|\bb-ad[ap]\b' .
   ```

   The pattern also finds `adp` or `ada` as any class and in any CSS
   selector, since a class attribute may list other classes in between. Read
   every hit. Search wider than `docs/`: pages, fragments, project CSS,
   inline `style` attributes, SVG figures, and the scripts that generate
   figures, which write these classes into their output. Leave historical
   records and old worklog entries as written.
2. Rename each use in the source. For a generated figure, change its generator
   and run it again; do not edit the output by hand. When the generator's
   environment no longer exists, recreate it from the project's setup guide,
   as [dependencies](../../../../rules/engineering/code.md#dependencies) asks
   of that guide. When it cannot be recreated, the figure keeps its old class
   until the owner decides; record the question as an unanswered one, as
   [unanswered questions](#unanswered-questions) describes.
3. Where the project set its own colour with `--adp: …` or `--ada: …`, set
   `--accent` or `--secondary` instead.
4. Rebuild, and look at each changed page at the widths the site supports.

Done when the search lists only the records left as written. No check enforces
this step.

## Colour navigation groups

The theme no longer colours five groups by name: `method`, `road`, `racing`,
`sim` and `related work`, written exactly so, in lower case. These were the
groups of the kit's first consumer. A project with none of these group names
sees no change and can skip this step, unless it wants fixed group colours.

Without settings, every group now takes the shared tones of `nav.js`, in
order. A colour that the project's own CSS sets for a group, through `--g`,
stays with or without the table; such a group needs no line. A new
`[group_colors]` table in `docs/site/site.toml` gives a group a
fixed colour for the whole site:
[authoring](../../../../rules/site/authoring.md#authoring-paths) describes it.
For the five former names the theme used these values:

```toml
[group_colors]
"method" = "#85b7eb"
"road" = "#ffb35c"
"racing" = "#6ee7c5"
"sim" = "#b69cff"
"related work" = "#8394a7"
```

1. Add the table above the first `[[nav]]` table, with one line for each group
   that should keep a fixed colour. Each name is the `group` of a visible
   `[[nav]]` entry, written exactly as there, including case. The old rules
   matched exact lower-case names only, so a group named `Related work`, for
   example, never had the fixed colour and showed a tone already.
2. Use hex colours only: `#rgb`, `#rgba`, `#rrggbb` or `#rrggbbaa`. The build
   stops on any other value, on a name that no visible `[[nav]]` entry uses,
   and on a value that is not a table.
3. The colour applies to the group's sidebar header and page links, its
   home-page map group and the top edge of its map cards, and the build-sheet
   chapter numbers of its pages. The old theme gave the map cards of `road`,
   `racing`, `sim` and `related work` other edge colours than their sidebar
   colours; with the table the cards take the group colour. A project that
   wants the old edges sets them in its home page's own CSS.
4. The build writes the table to `assets/group-colors.css` and links it on
   every page right after `base.css`. A page's own CSS, loaded later, still
   wins with a selector at least as strong as `.toc [data-group="…"]`. A
   project rule that sets `--g` with a weaker selector, such as
   `[data-group="…"]` alone, loses to the table for a group the table names.
5. A project asset under `[extra_assets]` named `group-colors.css` now fails
   the build when the table is set; rename it. `site.toml` has no check for
   unknown top-level keys, so a project that already used a key named
   `group_colors`, `plot_toggle_labels` or `worklog_links_checked_from` for
   something else renames its own key.
6. Rebuild, and look at the sidebar, the home-page map and one build-sheet
   page, wide and narrow.

Done when the build passes and the captures show the intended colours. The
build checks the table; nothing checks whether a group lost a colour it had.

## Label plot toggle chips

The `plot-toggles` component no longer holds chip labels. Up to 3.2.1 it
labelled nine group keys itself; they were plot series of the kit's first
consumer. Now a chip shows its group key unless a `[plot_toggle_labels]` table
in `docs/site/site.toml` gives it a label:
[authoring](../../../../rules/site/authoring.md#authoring-paths) describes it.
A project whose pages do not list `plot-toggles` in `components`, or whose
figures use none of the nine keys, sees no change and can skip this step.

The removed labels, as the table to copy:

```toml
[plot_toggle_labels]
"pinned" = "κ=0 joints"
"menger" = "Menger joints (default)"
"stacked" = "optimized joints"
"heuristic" = "Menger heuristic"
"free_psi" = "free_psi"
"free_kappa" = "free_kappa"
"free_both" = "free_both"
"corridor" = "road corridor"
"waypoints" = "waypoints"
```

1. Find the pages that load the component and the group keys their figures
   use; a group is every element whose `id` is `tg-<key>--<n>`:

   ```bash
   grep -rln 'plot-toggles' --include='*.md' docs/topics
   grep -rhoE 'tg-[A-Za-z0-9_.-]+--[0-9]+' --exclude-dir=.build --exclude-dir=.docs-kit --exclude-dir=.git . | sort -u
   ```

2. Add the table above the first `[[nav]]` table, with one line for each key
   the figures use. `free_psi`, `free_kappa`, `free_both` and `waypoints` were
   labelled with their own key, so they need no line.
3. Rebuild, and look at the chips of one figure on the page and in the
   lightbox, wide and narrow.

Done when every chip shows the intended label. Nothing enforces this: a key
without a line shows the key itself, for example `menger` in place of
"Menger joints (default)". The build rejects only a value that is not text
and a `plot_toggle_labels` that is not a table.

## Remove references to the pin button

The chapter reader built a `reader-drawer-pin` button and never added it to
the page. The button, its script and its two CSS rules are gone. Docking, its
stored choice and the close and menu buttons are unchanged, so readers see no
difference.

```bash
grep -rn 'reader-drawer-pin' --exclude-dir=.docs-kit --exclude-dir=.build --exclude-dir=.git .
```

Remove the project CSS rules and test assertions it finds. Done when the
search finds nothing outside historical records. No check enforces this.

## Replace tests that import the kit's tooling

Importing modules from `.docs-kit/tooling` is not among the
[stable interfaces](../releases.md#100--first-stable-version), and such a test
breaks when the kit changes inside. The comparison of every topic page with and
without the chapter reader moved from the kit's tests into
`tooling/reader_content.py`, and the kit now offers it as a command:

```bash
python .docs-kit/docsite.py build --project . --check-reader
```

Run it with the project's documentation interpreter, as in
[move the pin](#move-the-pin). It writes nothing and exits with status 1 when
the reader changes a page's
words, links, media, tables, folds, anchors or SVG figures. With
`chapter_reader` off it says so and exits 0.

1. Find project code that loads kit modules:

   ```bash
   grep -rnE 'docs-kit/tooling|sys\.path.*docs-kit|import (build|lint|site_paths|reader_content)\b' --include='*.py' --include='*.cjs' --include='*.js' --exclude-dir=.docs-kit --exclude-dir=.build .
   ```

   The search also finds two kinds of file this step does not change. A
   figure generator that imports `tooling/svg_figures.py` uses the shared
   figure markup that [generated figures](../../../../rules/site/authoring.md#generated-figures)
   describes; that module is a provisional interface, listed in the
   [1.0.0 notes](../releases.md#100--first-stable-version), and the import
   stays. A script kept as historical evidence, such as one that a run record
   pins, stays as written, as the theme step leaves historical records.
2. Replace a test that compares reader and plain pages with the command above,
   in the project's checks and in its hosted workflow.
3. A test that needs another kit module stays at the project's risk. The
   path and lint modules take the project root from `DOCSITE_PROJECT_ROOT`, or from the
   working directory when it is unset; `docsite.py` sets it. Run such a test
   from the project root, or set the variable. If the project needs that
   behaviour as an interface, report it to the kit instead.

A project that uses the chapter reader adds the command to its checks whether
or not it had a comparison test before: [validation](../../../../rules/site/validation.md#validation-and-review)
names it as the check of the reader.

Done when no project test imports the kit's build module for the reader
comparison and the project's checks run `--check-reader`. No check enforces
this.

## Review what changed without an edit

- **Asset URLs.** Pages load shared files as `assets/<file>?v=<hash>`. These
  shared files changed, so their query changes in every page that loads them:
  `base.css`, `chapter-reader.css`, `chapter-reader.js`, `panel-switcher.css`,
  `plot-toggles.js`, `slide-face.css`, `home.css`, `build-sheet.css`, and the
  `SOURCE.txt` notices of three fonts. A project check that compares built pages or asset names
  with a baseline compares the URL path without the query.
- **Built files.** A site with `[group_colors]` gains
  `html/assets/group-colors.css`. A project that compares or publishes its
  generated file list adds it. No other file is added or removed from a build.
- **Lint messages.** A configuration error in `site.toml` used to be reported
  by lint as a stale site. Lint now prints the build's own error message.
- **Worklog as a source page.** With `worklog_links_checked_from` set and the
  worklog registered as a source page, the build no longer fails on a missing
  link target in an entry dated before that day: the link renders as its
  text, unlinked, in `<span class="link-gone">`. Newer entries fail as before,
  and the build now rejects a value that is not a date;
  [resources](../../../../rules/site/resources.md#resource-closure-and-evidence)
  describes it.
- **Slide faces.** `slide-face.css` gains `slide-points`, `slide-facts` and a
  keyed `figcaption.slide-legend` inside `slide-figure`;
  [slide faces and decks](../../../../rules/site/authoring.md#slide-faces-and-decks)
  lists them. Existing faces render as before.
- **Generated figures.** A figure manifest needs the generator and the input
  data. `commit`, `date` and output-hash fields may be dropped, because Git
  holds them; lint reads only `script`, before and after this release.

## Apply the changed rules

No check enforces these rules. The
[conformance check](../../../../rules/conformance.md) asks the upgrade to fix
what it requires and to route other fixes through `OPEN.md` to their owner.
Each item below says what the owner decides. A question the owner has not
answered is written into open work as an unresolved choice, as the next item
but one describes.

### Finished working documents

[Finished working documents](../../../../rules/records.md#finished-working-documents):
a plan, decision record, review or coordination note is deleted once its work
has landed and its lasting content is in the owning record. Git keeps it;
whatever still needs it cites the commit and path.

1. List the finished working documents the project keeps as unedited copies,
   for example under an `evidence/` folder or in a location manifest. The rule
   names four kinds: a plan, a decision record, a review and a coordination
   note. A plan or protocol that a run copied and recorded by hash is one of
   them: once a record gives its commit, path and hash, they stand for it, as
   [numbers and staleness](../../../../rules/records.md#numbers-and-staleness)
   says, and the copy can go. Other kept files are not finished working
   documents and follow their own rules: an archived earlier publication is
   generated output, kept or ignored as the project's
   [generated files](../../../../rules/engineering/code.md#generated-files)
   rules say, and copied tool sources follow the source-of-a-run rules in the
   same section. Name such files in the report.
2. Move a rule that is still in force into a current record first.
3. Propose the deletion to the owner with the list. Nothing is deleted without
   the owner's approval.
4. After approval, delete the files, and change each link that still needs one
   into a link to the file at its commit. A hash recorded for the document
   stays valid, because Git returns the same bytes.
5. Old worklog entries keep their links; use `worklog_links_checked_from` as
   in [repoint links](#repoint-links-to-the-removed-section).
6. Remove the project's path adapter and evidence adapter once no record that
   is not edited afterwards, such as an old worklog entry or a historical
   experiment record, names an old path.
   [Resources](../../../../rules/site/resources.md#resource-closure-and-evidence)
   says so. The hooks `path_resolver`, `evidence_validator` and
   `document_origin` still work in 4.0.0.

Done when the owner has answered and the approved deletions have landed.

### Unanswered questions

[Decisions and blockers](../../../../rules/engineering/delivery.md#decisions-and-blockers):
a question for the person does not exist only in chat. Before stopping work or
reporting completion, write each unanswered question into the open owner as an
unresolved choice, with the options, the recommendation and what waits on it,
routed from `OPEN.md`. Done when the project's agent instructions and open
work follow it.

### Branches and worktrees

[Parallel work](../../../../rules/engineering/delivery.md#parallel-work): work
alone happens in the project's checkout on its current branch. A separate
branch or worktree is used only when other work changes the same repository at
the same time, when a running job depends on files the work would change, when
the project's workflow asks for one, or when the person asks for one. 3.2.1
said only that isolation is used when independent work
requires it, and agents had started to give every piece of work its own branch
and worktree.

1. A project whose workflow asks for a branch per change, for example for
   review, states that in its own development guide. Without such a statement
   the default applies.
2. Branches and worktrees that earlier work left behind are not removed by
   this step. Name them to the owner with their state and propose what to do
   with each.

Done when the project's guide states its workflow or relies on the default.
Nothing enforces it.

### Run output

[Numbers and staleness](../../../../rules/records.md#numbers-and-staleness):
the run output a stated number or verdict rests on is tracked in the
experiment directory before the experiment is reported complete. Output only
in an untracked build or temporary folder is not retained, and a claim that
rests on it is not measured. 3.2.1 let a project keep bulky files outside Git
on its own; that sentence is gone.

1. For each experiment the project reports as complete, check that the output
   behind its stated numbers and verdicts is tracked in its directory.
2. Keeping output outside Git is the owner's decision. Ask, with the size and
   the options. Until the owner answers, record the question as an unresolved
   choice and state in the experiment directory where the files are.
3. Output that no stated number or verdict rests on is named in the report
   with a proposal to delete it.

Done when each complete experiment has its output tracked or an answered
decision recorded.

### Source of a run

The same section: code that was not committed when a run started is kept as a
diff against the commit the run started from, with new files and submodule
changes, and that commit is recorded. A run does not copy the working tree. A
copy that cannot be avoided holds no ignored files, and an ignored file the run
reads is recorded as an input by its identity. Change project run tooling that
copies the working tree. Earlier run records stay as written.

### Finished probe scripts

[Refactoring over compatibility](../../../../rules/engineering/code.md#refactoring-over-compatibility):
a full refactor deletes a caller that is a finished probe or one-time script
instead of updating it, when nothing else imports it, no rerun is planned and
its result is recorded with a source pin that stands for it. Claims that rest
on it are historical from then on, and the pin still stands for the code after
the deletion. A script kept in an experiment directory is covered too. Nothing
to change now: the rule applies to the next refactor
that meets such a script. It creates no duty to search for old scripts.

### Dependencies

[Dependencies](../../../../rules/engineering/code.md#dependencies): every
dependency the code needs is declared in the project's dependency file and
installed into the environment. Code does not load a library from an untracked
checkout or a folder under build output. A vendored copy carries its license
and a notice of its source and version. A pinned Git submodule such as
`.docs-kit` counts as declared. Declare what is missing, and check that the
setup guide, followed from a fresh clone, produces the environment the project
runs.

### Scratch files and captures

[Scratch files](../../../../rules/engineering/handoffs.md#scratch-files): an
agent deletes the untracked drafts, review captures and temporary test folders
its own work created before it reports completion. A record cites no scratch
file by path or hash; it states what the review found.

1. Find citations of review captures by path or hash in the project's records.
   Remove them from current records and state the finding in words instead.
   Old worklog entries and historical experiment records stay as written.
2. Captures left from earlier work were not created by this upgrade. Name them
   in the report and propose their deletion; tracked captures need the owner's
   approval to delete. A capture a page uses as a figure is not scratch. The
   upgrading agent cannot tell whether another session still needs a folder
   of its own; list each with its path, date and size, and the owner decides.

### One README

[README is the bounded exception](../../../../rules/documentation.md#readme-is-the-bounded-exception):
a repository has one `README.md`, at its root. Files that arrive with
third-party code keep their names. A notice that the project wrote itself,
for example the source note of vendored data, did not arrive with third-party
code: it is renamed like any other guide, for example to `SOURCE.md`.

```bash
git ls-files | grep -E '(^|/)README\.md$' | grep -v '^README\.md$'
```

1. With the owner, rename each hit to a name for its subject, such as
   `experiments/<name>/<name>.md`, with `git mv`.
2. Correct the links to it; lint reports each one that is still wrong. A
   `[[source_pages]]` `source` that names it must change too; the build stops
   on a missing source.
3. A run record that pinned the file by hash keeps the old path: the commit,
   the path at that commit and the hash still identify the bytes.

Lint does not enforce the rule. The conformance check lists it under topics.

### Names on pages

[Page design](../../../../rules/writing/pages.md#page-design): a page that
explains how something works names the people who do the work by role, with
one role word for each role. A name stays where the page states who decided,
approved or said something, and in a method's name, a citation or a contact
line. Reread such pages and replace names with role words. Pages locked by
hash need an approved content revision first.

To find the names, list the people Git knows and search the pages for each:

```bash
git log --format='%an%n%cn' | sort -u
grep -rniF -e '<name>' --include='*.md' --include='*.html' docs/topics
```

A user name inside a path, also in data that a page carries, is a name too:
replace it, as the rule says from 5.0.0.

### Slide faces

[Slide faces](../../../../rules/writing/pages.md#slide-faces): faces come after
the chapters and only when the person says yes. A face shows one finding with
a real visual; a face whose main area only repeats its title and lead in boxes
is removed, and a chapter with nothing to show gets no face.

1. Add no new face without the person's yes.
2. Review each existing face against the new rules and list the faces that

### Missing figures

completion report says so. This applies to the next page work; no existing
page needs an edit for it.
