# Migrate to kit 5.0.0

This guide applies the [5.0.0 release notes](../releases.md#500--reference-section-by-default-page-lock-and-presentation-view)
to an existing 4.0.0 consumer. Prepare the upgrade as in the
[1.1.0 guide](1.1.0.md#prepare-the-deliverable): record the old and new kit
commits, keep a baseline build and follow the project's permissions and staging
workflow.

A project on an older version follows the earlier guides first, oldest first,
for their content steps, and then this one. It still moves its pin once,
straight to `v5.0.0`; it does not pin each release in between.

6.0.0 changed what this guide's first two sections describe: the Reference
section lists only `docs/`, or the folders a project names instead, and
`reference_exclude` is removed. A project that moves on to 6.0.0 skips those
two sections and follows the [6.0.0 guide](6.0.0.md) for them, with the tag
`v6.0.0` wherever this guide writes `v5.0.0`.

## Read this before the pin moves anywhere that publishes

**With 5.0.0, every tracked Markdown file of a project becomes a page of its
site.** The files are listed in the sidebar's Reference section and published
with the site. A private repository with a public site therefore publishes its
records, plans, agent files and notes at the next publish, unless it excludes
them or turns the listing off. No check stops this: the build passes, and lint
prints only `NOTE:` lines.

Do the first step below before a commit with the moved pin is pushed to any
branch whose push publishes the site, and before `publish` runs on it.

The [release notes](../releases.md#500--reference-section-by-default-page-lock-and-presentation-view)
say why 5.0.0 is a major release. After the steps below, run the
[project conformance check](../../../../rules/conformance.md) and report its
findings.

| Step | Who needs it | Enforced by |
|---|---|---|
| [Settle what the Reference section lists](#settle-what-the-reference-section-lists) | Every project; first of all a private repository with a public site | Nothing |
| [Move the pin](#move-the-pin) | Every project | Lint (pin check) |
| [Rename own keys with the new names](#rename-own-keys-with-the-new-names) | A project whose `site.toml` already has a top-level key with a new name | The build |
| [Set the tooling folders](#set-the-tooling-folders) | Every project | Lint |
| [Unregister private source pages](#unregister-private-source-pages) | A project whose `[publication]` private prefixes or suffixes cover a registered file | `publish` |
| [Remove the adapter hooks](#remove-the-adapter-hooks) | A project whose `site.toml` names `path_resolver`, `evidence_validator`, `evidence_manifests` or `legacy_files`; deleting its old documents needs the owner's yes | The build; lint for the links |
| [Repoint or remove dead HTML links](#repoint-or-remove-dead-html-links) | A project whose pages hold HTML links to repository files | Lint |
| [Fix formulas that do not compile](#fix-formulas-that-do-not-compile) | A project with `math = true` pages | Lint, where it finds Node.js |

## Settle what the Reference section lists

[Automatic reference listing](../../../../rules/site/authoring.md#automatic-reference-listing)
has the full rule. A tracked `.md` file is listed unless it lies inside a Git
submodule, such as `.docs-kit/`; has a folder or file name in its path that
starts with a dot; starts with `+++` frontmatter or is a topic entry page; is
a symbolic link or lies below one; matches a `reference_exclude` pattern; or
is covered by the `private_prefixes` or `private_suffixes` of the
`[publication]` table. A file with `---` YAML frontmatter is listed and shows
the frontmatter as text. Raw HTML in a listed file keeps only the tags and
attributes the rule admits; any other tag shows as text. Agent files such as
`AGENTS.md` are listed unless excluded.

1. List the candidates. In 4.0.0, from the project root, this prints the files
   the listing would take before `reference_exclude` and the private prefixes
   and suffixes apply; with `.md` among the private suffixes, nothing will be
   listed:

   ```bash
   git ls-files -s -- '*.md' | awk '$1 != "120000"' | cut -f2 | grep -vE '(^|/)\.' | while IFS= read -r f; do head -c3 -- "$f" | grep -q '^+++' || printf '%s\n' "$f"; done
   ```

   The list includes the files that `[[source_pages]]` tables already
   register; they stay listed as before.
2. Decide with the owner which files may be public. For a private repository
   with a public site, the owner decides this file by file or folder by folder.
3. Write the decision into `docs/site/site.toml`, above the first `[[nav]]`
   table. Either exclude what must not be listed:

   ```toml
   reference_exclude = ["CLAUDE.md", "experiments/**", "notes/"]
   ```

   or list only the `[[source_pages]]` tables, as in 4.0.0:

   ```toml
   reference_listing = false
   ```

   `*` and `?` stay within one folder, `**` spans folders, and a pattern ending
   in `/` matches everything below that folder; the rule gives the rest. 4.0.0
   does not check unknown top-level keys, so both settings can be written
   before the pin moves.
4. After [moving the pin](#move-the-pin), and once the build passes, print the
   files that are listed automatically:

   ```bash
   python -c "import json, sys; d = json.load(open('.build/docs/site-build.json')); 'reference_tree' in d or sys.exit('site-build.json is not from kit 5.0.0; build first'); print('\n'.join(sorted(s for r, s in d['source_pages'].items() if r.endswith('.md.html'))))"
   ```

   Run it with the project's documentation interpreter. Registered pages have
   routes without `.md`, so the command prints only the automatic ones. The
   built sidebar's Reference section shows the same files.
5. Compare the printed list with the decision. Change `reference_exclude`,
   rebuild and repeat until the list holds only files the owner approved.

Done when the owner has approved the printed list, or `reference_listing =
false` is set. No check enforces this step.

## Move the pin

1. Fetch the tag and check it out:

   ```bash
   git -C .docs-kit fetch --tags origin
   git -C .docs-kit checkout v5.0.0
   ```

   `requirements.txt` is unchanged since 4.0.0, so the documentation
   environment needs no reinstall. `requirements-lock.txt` is new and needed
   only for the [page lock](#adopt-the-page-lock).
2. Rebuild and run lint with the project's documentation interpreter,
   written `python` here; the [4.0.0 guide](4.0.0.md#move-the-pin) says how to
   find or create it in a fresh clone or worktree:

   ```bash
   python .docs-kit/docsite.py build --project .
   python .docs-kit/docsite.py lint --project . --strict
   ```

   A build error that names a removed or renamed setting is fixed in a step
   below; do that step, then come back. Lint fails with the errors the steps
   below fix: `tooling_roots` until it is set, and the HTML link, formula and
   slide-face checks. A problem in an automatically listed file is a
   `NOTE: reference page …` line, which never fails; on a file that should not
   be listed it is a reason to exclude the file, not to edit it.
3. In a fresh clone or worktree whose recorded pin cannot be fetched,
   `git submodule update --init` stops with `not our ref`; the
   [4.0.0 guide](4.0.0.md#move-the-pin) describes what a consumer did.

Done when `git -C .docs-kit describe --tags` prints `v5.0.0` and the build
passes. Lint fails while the pinned commit is on none of the kit's remote
branches; a tag alone does not count. A link to a file that exists on one
machine but is not tracked passes lint there and fails in a fresh clone, so
run the checks in a fresh clone before landing.

## Rename own keys with the new names

`reference_listing`, `reference_exclude`, `tooling_roots`, `capability_map`,
`experiment_roots` and `formula_check_required` are new top-level keys of
`docs/site/site.toml`. A project that already used one of these names for its
own value now fails the build when the value is not valid for the new
setting, for example with `site.toml: reference_listing must be true or false`.

```bash
grep -nE '^\s*(reference_listing|reference_exclude|tooling_roots|capability_map|experiment_roots|formula_check_required)\s*=' docs/site/site.toml
```

Rename a project key that the search finds and that the project did not write
for this guide, and change the project code that reads it. Done when the build
passes.

## Set the tooling folders

Every project now sets `tooling_roots`, and lint fails without it. A project
with tooling keeps a capability map; [the capability map](../../../../rules/engineering/code.md#the-capability-map)
says why, and [capability map settings](../../../../rules/site/authoring.md#capability-map-settings)
give the format and the check.

1. Find the project's tooling: folders of scripts, harnesses, judges or other
   [supporting code](../../../../rules/engineering/code.md#name-the-need-first).
   Without any, write `tooling_roots = []` above the first `[[nav]]` table of
   `docs/site/site.toml`; the step is done.
2. Otherwise copy the starter's empty map and link it from `docs/index.md`:

   ```bash
   cp .docs-kit/examples/starter/docs/CAPABILITY_MAP.md.tmpl docs/CAPABILITY_MAP.md
   ```

3. Write one row for each need that the code directly under the tooling
   folders meets, each need worded without naming an experiment, with a link
   to its code and its state. Leave the Imported by cells empty.
4. Set `tooling_roots` to those folders, as the settings show, then fill the
   generated column and lint:

   ```bash
   python .docs-kit/docsite.py capability-map --project .
   python .docs-kit/docsite.py lint --project . --strict
   ```

5. Add the starter's route "Building tooling, a harness or other supporting
   code" from `.docs-kit/examples/starter/AGENTS.md.tmpl` to `AGENTS.md`.

A warning for a tool that imports from an experiment folder names code to move
into the tooling tree; moving it is a refactor for the owner to schedule.
Route each such finding through `OPEN.md`, and leave `experiment_roots` unset
until the owner decides, so that strict lint passes. Done when strict lint
reports no capability map error and the owner has the list of findings.

## Unregister private source pages

`publish` now fails when a `[[source_pages]]` table registers a file that the
`[publication]` `private_prefixes` or `private_suffixes` cover, with
`Private source cannot be published as a page: <file> (<route>)`. Up to 4.0.0
such a page was published. A project with `.md` among its private suffixes
and any `[[source_pages]]` table meets this.

1. Look at the `[publication]` table and the registered sources:

   ```bash
   grep -nE '^\s*(private_prefixes|private_suffixes|source)\s*=' docs/site/site.toml
   ```

2. For each registered file that a prefix or suffix covers, the owner decides:
   the file is private, and its `[[source_pages]]` table is removed; or the
   file is public, and the prefix or suffix is narrowed. A narrowed prefix or
   suffix can list many more files, all of them with `.md` removed from the
   suffixes: go back to the [first step](#settle-what-the-reference-section-lists)
   before anything is published.
3. Run `publish` into a new folder outside the project, for example
   `python .docs-kit/docsite.py publish --project . --out /tmp/site-check`,
   and delete that folder after the check.

Done when `publish` passes.

## Remove the adapter hooks

A project whose `docs/site/site.toml` names `path_resolver`,
`evidence_validator`, `evidence_manifests` or `legacy_files` fails the build
with `site.toml: path_resolver was removed in kit 5.0.0` or the same message
for the other setting. The kit no longer loads a project's path or evidence
adapter, verifies collections of exact-byte copies, or maps old paths to
current files. These settings let a project keep old documents as unedited
copies in its live tree; since 4.0.0 a finished working document is deleted
and cited from Git instead. The
[resources rule](../../../../rules/site/resources.md#resource-closure-and-evidence)
describes what holds now.

```bash
grep -nE '^\s*(path_resolver|evidence_validator|evidence_manifests|legacy_files)\s*=' docs/site/site.toml
```

1. List the old documents these settings serve: the copies the adapter's
   mapping or a declared evidence manifest names, the old paths of
   `legacy_files`, and what still links to them. A hash that a record states
   for such a document stays valid for the file at its commit. Deleting a
   document is the project owner's decision: bring the list and wait for the
   owner's yes, as [rules for changes and chronology](../../../../rules/documentation.md#rules-for-changes-and-chronology)
   says. The owner may approve some files and keep others.
2. Delete the approved copies under
   [finished working documents](../../../../rules/records.md#finished-working-documents).
   First move a rule that is still in force into a current record. Where
   something still needs a deleted document, cite its commit and path.
3. Remove the settings, and the manifests and tests that only the adapter or
   the kit's evidence check read. Remove the adapter file once a search, such
   as `git grep -n layout_paths` for `docs/site/layout_paths.py`, finds no
   other user; a project test that imports it keeps it until that test
   changes.
4. Run `python .docs-kit/docsite.py lint --project . --strict`. A link that
   needed the adapter is now a dead link or a missing anchor, in the Markdown
   link check or in the new check of HTML links. Repoint it to the current
   file or to the file at its commit, or remove it, as the
   [next step](#repoint-or-remove-dead-html-links) says. Do not rewrite old
   worklog entries: set `worklog_links_checked_from` to the date of the oldest
   entry whose links still resolve, as the resources rule describes.
5. Lint's Markdown link check covers `docs/`, `AGENTS.md`, `CLAUDE.md`,
   `README.md`, registered source pages and the capability map. Records
   elsewhere that only the removed evidence settings brought into it are no
   longer checked; an automatically listed one gets notes at most. List their
   dead links once, and repoint or remove each:

   ```bash
   python - <<'EOF'
   import os, re, subprocess
   from urllib.parse import unquote
   for f in subprocess.check_output(['git', 'ls-files', '*.md'], text=True).splitlines():
       if f.startswith('docs/') or f in ('AGENTS.md', 'CLAUDE.md', 'README.md'):
           continue
       text = re.sub(r'`[^`]*`', '', re.sub(r'```.*?```', '', open(f).read(), flags=re.S))
       for target in re.findall(r'\]\(([^)\s#]+)', text):
           path = unquote(target.split('?')[0])
           if not re.match(r'[a-z][a-z0-9+.-]*:|//', target, re.I) and not os.path.exists(os.path.join(os.path.dirname(f), path)):
               print(f'{f}: dead link {target}')
   EOF
   ```

Done when the build and `lint --strict` pass with none of the four settings,
and the command above prints nothing the owner has not accepted.

## Repoint or remove dead HTML links

Lint now checks a link written as HTML, `<a href="…">`, that points at a
repository file: in a topic page, in a fragment the page includes and in a
registered source page. The target must exist, and a fragment into a
Markdown file must match one of its anchors;
[authoring paths](../../../../rules/site/authoring.md#authoring-paths)
describes the check.

```bash
python .docs-kit/docsite.py build --project .
python .docs-kit/docsite.py lint --project . --strict 2>&1 | grep -E 'dead link to repository file|anchor #.* not found in'
```

For each line, open the page's source that the message names; the built page
in brackets tells which page includes the link when it sits in a fragment.
When the file moved, point the link at its current path. When it is gone and
the link still matters, link the file at the commit that had it, or the record
that took over its content. When the link no longer helps the reader, remove
it and keep the text. When the anchor changed, link the current heading. A
page whose words the project locks by hash needs an approved content revision
first, as the [3.0.0 guide](3.0.0.md#topic-records) says.

Done when `lint --strict` reports neither message.

## Fix formulas that do not compile

Lint now compiles every formula on the built pages with the KaTeX the kit
ships, as [formula check](../../../../rules/site/authoring.md#formula-check)
describes. It runs Node.js for that one check: `DOCS_NODE` when set, otherwise
`node` on `PATH`. Building still needs no Node.

1. Rebuild and run lint where Node is installed, and look at the formula
   lines:

   ```bash
   python .docs-kit/docsite.py build --project .
   python .docs-kit/docsite.py lint --project . 2>&1 | grep -E 'formula'
   ```

   Each failure is an `ERROR:` line that names the page's source, the built
   page and the formula: `formula does not compile` with KaTeX's message,
   `formula split by Markdown`, or `formula not closed in the same text`.
   Without Node the check prints a `NOTE: formula check skipped` line instead.
2. Correct each formula in its source. A formula that Markdown split usually
   holds an underscore or asterisk that Markdown read as emphasis; inside raw
   HTML write it as `\(…\)`, as [mathematical explanation](../../../../rules/writing/math.md#mathematical-explanation)
   says. A formula that worked in the browser only because a project script
   defined a macro is a case for the owner: the check knows the kit's KaTeX
   settings only.
3. Decide with the owner whether the project's checks must have the formula
   check. If so, set `formula_check_required = true` above the first `[[nav]]`
   table of `docs/site/site.toml`, and install Node.js wherever lint runs, the
   hosted workflow included.
4. A project test that compiles the formulas of its built pages itself, such
   as ADP's `tools/docs/test_content_math.cjs`, may be dropped, or reduced to
   the project's own assertions, once lint runs the check with Node.

Done when lint reports no formula error with Node installed, and the owner
has decided on `formula_check_required`.

## Settle the slide-face checks

Lint now reads the slide faces of the built pages, as
[slide faces and decks](../../../../rules/site/authoring.md#slide-faces-and-decks)
describes, and the shared browser check measures faces below 720 px. A project
with slide faces does three things once the pin has moved and the site is
built:

1. **Find chapters with two faces.** Run
   `python .docs-kit/docsite.py lint --project .`. Each chapter with more than
   one face, each face that does not open its chapter and each face outside
   every chapter is an `ERROR:` line that names the page and the chapter.
   Keep one face per chapter, at the chapter's start. Which face stays is the
   owner's decision when both are worth keeping.
2. **Settle the number findings.** Run
   `python .docs-kit/docsite.py lint --project . --strict`. Each
   `WARN: … numbers shown only on the slide face: …` line names the page, the
   chapter and the numbers. For each number, state it in the chapter with its
   evidence, or correct the face. When the finding is false, because the
   chapter shows the number in a form the check does not read, such as a
   picture, a script or a rounded value, wrap that one number on the face in
   an element with `data-face-only="<reason>"`; lint then prints it as a
   `NOTE:` line.
3. **Check faces in the browser at phone width.** In the project's browser
   review, open each chapter with a face at 390 px and at the reader widths
   the site supports, and call `goHash` and `assertSlideFaces` from
   `.docs-kit/tooling/browser_checks.cjs`, as
   [reusable browser checks](../../../../rules/site/validation.md#reusable-browser-checks)
   shows. The helper needs Playwright, which the project installs itself; the
   kit's own `node_modules/` is only for its own checks. A browser review that
   does not use the kit's helper takes over its checks: no sideways overflow,
   no cut text, no part outside the face, a 16:9 face that fits, and drawing
   labels at 11 px or more. A wide SVG drawing scaled into a phone column
   shrinks its labels with it: give the face an upright drawing for narrow
   widths, as the kit's example faces do, or larger labels. Rows of
   `slideFaces` for faces the page does not show now carry only `chapter`,
   `shown: false` and `problems`; a harness that reads `fits` or `width`
   checks `shown` first.

Done when `lint --strict` passes, the owner agrees with the reason of every
accepted number, and the browser review checks every face at 390 px.

## Review slide faces

This step is optional. [Slide faces](../../../../rules/writing/pages.md#slide-faces)
no longer prescribe one arrangement of lead, visual, points and facts row.
Each face's layout follows the shape of its content, and the faces of a
project share a frame. Existing faces still build and render as before. To
apply the rule, sort each face into one of three groups, with the reason: a
face without a real visual, or on a chapter with nothing to show, is redrawn
or removed; a face with a real visual whose layout is below the rule's
standard is redesigned; any other face stays.

```bash
grep -rln '^<!-- slide -->' --include='*.md' docs/topics
```

Removing or redrawing a face changes the page, and a project may count its
faces in checks or lock pages by hash. Ask the owner first. Done when the
owner has the list with its groups, or has decided to skip the review.

## Adopt the page lock

This step is optional. A project that does not set `lock = true` publishes
the same bundle as before. [Page lock](../../../../rules/site/publication.md#page-lock)
has the setup, what is locked and the limits; read the limits with the owner
before adopting it. The lock is not access control: the encrypted files are
public, and anyone who has a password can read and pass on what it opens.

1. Install the optional dependency wherever `publish` runs, in the hosted
   workflow too:

   ```bash
   python -m pip install -r .docs-kit/requirements-lock.txt
   ```

2. Set `lock = true` in the `[publication]` table of `docs/site/site.toml`.
3. Create two passwords and store them as repository secrets named
   `DOCSITE_GENERAL_PASSWORD` and `DOCSITE_REFERENCE_PASSWORD`. The general
   password opens the topic pages; the reference password opens everything,
   the Reference pages and exported Markdown files included. The rule says
   which passwords `publish` refuses and how to generate them.
4. Pass the two secrets only to the step that runs `publish`, as the rule's
   example shows, not to the whole job.
5. Deploy the `--out` directory of `publish`. The build output under
   `.build/docs/` stays plain: a workflow that deploys it, or uploads it as an
   artifact, publishes every page unlocked.
6. Keep the repository, its Actions logs and its workflow artifacts private.
   Whoever can change the workflow or the published site can replace the
   unlock script.
7. Run `publish` and read its summary with the owner: how many files each
   password opens, how many stay readable, and how many Reference pages are
   still linked from pages that the general password opens. Check the
   readable files for data that should not be public.

Done when a locked publish passes and the owner has read the summary. To
check the lock without the hosted workflow, set the two variables in the
shell and run `publish` into a new folder outside the project.

## Update checks that compare built output

A project whose own checks compare or read the build updates them for these
changes; the [release notes](../releases.md#500--reference-section-by-default-page-lock-and-presentation-view)
describe each.

| What the project's check does | What changed |
|---|---|
| Compares the generated file list | Above 60 listed files, or with the page lock on, the build writes `reference.tree.js` and `reference.index.html`; a page with the address `reference.index.html` then fails the build. Each automatically listed file adds a page, such as `readme.md.html` |
| Reads `source_pages` of `site-build.json` as the registered pages | It now maps the automatic routes too; the registered ones do not end in `.md.html`. The new key `reference_tree` names the two files or is `null` |
| Compares built pages with a baseline | `base.css`, `chapter-reader.css`, `chapter-reader.js`, `filelinks.js`, `lightbox.js`, `nav.js`, `plot-toggles.js` and `slide-face.css` changed, so their `?v=` query changes; compare the URL path without the query. Every page ends its sidebar with the Reference section when a file is listed, and the view menu of every page with a slide face gains Presentation options |
| Compares published pages byte for byte | `publish` marks each link it points at a published file with `data-repo-exported`; with `gh_repo = ""` it rewrites the source links of every generated page |
| Prints pages with slide faces from All chapters | All chapters hides the faces until its Slides switch is on |

Done when the project's own checks pass.

## Reread pages that explain changed guides

Reread the project pages that link a rule file changed since 4.0.0, as the
conformance check asks, and update each explanation in the page's own words.
This lists the changed files; the release notes' Rules, Lint and Theme rows
say what changed in each:

```bash
git -C .docs-kit diff --stat v4.0.0 v5.0.0 -- rules
```

## Land the upgrade

Commit the moved pin together with the settings and adaptations above, record
the old and new kit commits, the approved Reference list and the checks in the
project's worklog, and report the conformance findings with the owner's open
decisions. Push only after the [first step](#settle-what-the-reference-section-lists)
is done. [Pin and upgrade](../../../../README.md#pin-and-upgrade) has the
commands. A project whose run tooling refuses to start while paths are
uncommitted commits the moved pin first and runs the checks on that commit,
as the [4.0.0 guide](4.0.0.md#land-the-upgrade) describes.
