# Migrate to kit 5.0.0

This guide applies the [5.0.0 release notes](../releases.md#500--reference-section-by-default-page-lock-and-presentation-view)
to an existing 4.0.0 consumer. Prepare the upgrade as in the
[1.1.0 guide](1.1.0.md#prepare-the-deliverable): record the old and new kit
commits, keep a baseline build and follow the project's permissions and staging
workflow.

A project on an older version follows the earlier guides first, oldest first,
for their content steps, and then this one. It still moves its pin once,
straight to `v5.0.0`; it does not pin each release in between.

## Read this before the pin moves anywhere that publishes

**With 5.0.0, every tracked Markdown file of a project becomes a page of its
site.** The files are listed in the sidebar's Reference section and published
with the site. A private repository with a public site therefore publishes its
records, plans, agent files and notes at the next publish, unless it excludes
them or turns the listing off. No check stops this: the build passes, and lint
prints only `NOTE:` lines.

Do the first step below before a commit with the moved pin is pushed to any
branch whose push publishes the site, and before `publish` runs on it.

5.0.0 is a major release because of this changed default, and because
`publish` now refuses a `[[source_pages]]` table whose file is private. Apart
from the pin, the only edits that a check enforces are a renamed own key and a
private registered page. The other steps need the person who owns the project
to decide or approve. After the steps below, run the
[project conformance check](../../../../rules/conformance.md) and report its
findings.

| Step | Who needs it | Enforced by |
|---|---|---|
| [Settle what the Reference section lists](#settle-what-the-reference-section-lists) | Every project; first of all a private repository with a public site | Nothing |
| [Move the pin](#move-the-pin) | Every project | Lint (pin check) |
| [Rename own keys with the new names](#rename-own-keys-with-the-new-names) | A project whose `site.toml` already has a top-level `reference_listing`, `reference_exclude`, `tooling_roots`, `capability_map` or `experiment_roots` | The build |
| [Unregister private source pages](#unregister-private-source-pages) | A project whose `[publication]` private prefixes or suffixes cover a registered file | `publish` |
| [Check the path adapter](#check-the-path-adapter) | A project with a `path_resolver` | Nothing |
| [Review what changed without an edit](#review-what-changed-without-an-edit) | Every project | Nothing |
| [Review slide faces](#review-slide-faces) | A project with slide faces, optional | Nothing |
| [Adopt the page lock](#adopt-the-page-lock) | A project that wants it, optional | `publish` checks the passwords |
| [Adopt the capability map](#adopt-the-capability-map) | A project that keeps tooling or supporting code, optional | Lint, once `tooling_roots` is set |
| [Reread pages that explain changed guides](#reread-pages-that-explain-changed-guides) | A project whose pages link the changed guides | Lint notes for its own records only |

## Settle what the Reference section lists

[Automatic reference listing](../../../../rules/site/authoring.md#automatic-reference-listing)
has the full rule. A tracked `.md` file is listed unless it:

- lies inside a Git submodule, such as `.docs-kit/`;
- has a folder or file name in its path that starts with a dot, such as
  `.github/` or `.claude/`;
- starts with `+++` frontmatter, or is a topic entry page;
- is a symbolic link or lies below one;
- matches a `reference_exclude` pattern;
- is covered by the `private_prefixes` or `private_suffixes` of the
  `[publication]` table.

A file with `---` YAML frontmatter is listed, and the frontmatter shows as
text. Agent files such as `AGENTS.md` and `CLAUDE.md` are listed unless
excluded.

1. List the candidates. In 4.0.0, from the project root, this prints the files
   the listing would take before `reference_exclude` and the private prefixes
   and suffixes apply:

   ```bash
   git ls-files -s -- '*.md' | awk '$1 != "120000"' | cut -f2 | grep -vE '(^|/)\.' | while IFS= read -r f; do head -c3 -- "$f" | grep -q '^+++' || printf '%s\n' "$f"; done
   ```

   The list includes the files that `[[source_pages]]` tables already
   register; they stay listed as before.
2. Decide with the owner which files may be public. For a private repository
   with a public site, the owner decides this file by file or folder by folder.
3. Write the decision into `docs/site/site.toml`, above the first `[[nav]]`
   table. Either exclude what must not be listed:

   ```toml
   reference_exclude = ["CLAUDE.md", "experiments/**", "notes/"]
   ```

   or list only the `[[source_pages]]` tables, as in 4.0.0:

   ```toml
   reference_listing = false
   ```

   Patterns are matched against the whole repository-relative path: `*` and
   `?` stay within one folder, `**` spans any number of folders, and a pattern
   ending in `/` matches everything below that folder. A pattern has no
   leading `/`, no `\` and no `.` or `..` parts. 4.0.0 does not check unknown
   top-level keys, so both settings can be written before the pin moves.
4. After [moving the pin](#move-the-pin) and building, print the files that
   are listed automatically:

   ```bash
   python -c "import json; d = json.load(open('.build/docs/site-build.json')); print('\n'.join(sorted(s for r, s in d['source_pages'].items() if r.endswith('.md.html'))))"
   ```

   Run it with the project's documentation Python. Registered pages have
   routes without `.md`, so the command prints only the automatic ones. The
   build does not print the list itself. Open the built sidebar's Reference
   section to see the same files as a reader does.
5. Compare the printed list with the decision. Change `reference_exclude`,
   rebuild and repeat until the list holds only files the owner approved.

Done when the owner has approved the printed list, or `reference_listing =
false` is set. No check enforces this step.

## Move the pin

1. Fetch the tag and check it out:

   ```bash
   git -C .docs-kit fetch --tags origin
   git -C .docs-kit checkout v5.0.0
   ```

   `requirements.txt` is unchanged since 4.0.0, so the documentation
   environment needs no reinstall. `requirements-lock.txt` is new and needed
   only for the [page lock](#adopt-the-page-lock).
2. Rebuild and run lint with the project's documentation Python, for example
   `.build/docs-env/bin/python` where the project has that environment:

   ```bash
   python .docs-kit/docsite.py build --project .
   python .docs-kit/docsite.py lint --project . --strict
   ```

   When an automatically listed file has problems, the build prints
   ``note: N problem(s) in automatically listed reference pages were tolerated; `lint` lists them``,
   and lint prints each problem as a `NOTE: reference page …` line. Notes never fail. A note on a file that should not be listed is a
   reason to exclude it, not to edit it.
3. In a fresh clone or worktree whose recorded pin cannot be fetched,
   `git submodule update --init` stops with `not our ref`; the
   [4.0.0 guide](4.0.0.md#move-the-pin) describes what a consumer did.

Done when `git -C .docs-kit describe --tags` prints `v5.0.0`, and the build
and strict lint pass. Lint fails while the pinned commit is on none of the
kit's remote branches; a tag alone does not count.

## Rename own keys with the new names

`reference_listing`, `reference_exclude`, `tooling_roots`, `capability_map`
and `experiment_roots` are new top-level keys of `docs/site/site.toml`. A
project that already used one of these names for its own value now fails the
build when the value is not valid for the new setting, for example with
`site.toml: reference_listing must be true or false`. A valid list in its own
`tooling_roots` turns on the capability map check instead.

```bash
grep -nE '^\s*(reference_listing|reference_exclude|tooling_roots|capability_map|experiment_roots)\s*=' docs/site/site.toml
```

Rename a project key that the search finds and that the project did not write
for the [first step](#settle-what-the-reference-section-lists), and change the
project code that reads it. Done when the build passes.

## Unregister private source pages

`publish` now fails when a `[[source_pages]]` table registers a file that the
`[publication]` `private_prefixes` or `private_suffixes` cover, with
`Private source cannot be published as a page: <file> (<route>)`. Up to 4.0.0
such a page was published. A project with `.md` among its private suffixes
and any `[[source_pages]]` table meets this.

1. Look at the `[publication]` table and the registered sources:

   ```bash
   grep -nE '^\s*(private_prefixes|private_suffixes)\s*=' docs/site/site.toml
   grep -nE '^\s*source\s*=' docs/site/site.toml
   ```

2. For each registered file that a prefix or suffix covers, the owner decides:
   the file is private, and its `[[source_pages]]` table is removed; or the
   file is public, and the prefix or suffix is narrowed.
3. Run `publish` into a new folder outside the project, for example
   `python .docs-kit/docsite.py publish --project . --out /tmp/site-check`,
   and delete that folder after the check.

Done when `publish` passes. `publish` enforces this step.

## Check the path adapter

A project with a `path_resolver` in `docs/site/site.toml` meets two changes,
described in [resources](../../../../rules/site/resources.md#resource-closure-and-evidence):

- Within one build or lint run, the kit asks the adapter once per distinct
  path, root and recorded roots, and reuses the answer. An adapter whose
  answer depends on something that changes during the run, such as a counter
  or a file the run writes, now gives the first answer every time.
- The adapter now also receives the link targets of every automatically
  listed file, which may be paths it never saw before. For such a page a
  `ValueError` or `OSError` from the adapter counts as "no mapping", and the
  link is checked as written. Any other exception stops the build.

```bash
grep -nE '^\s*path_resolver\s*=' docs/site/site.toml
```

Read the named module. Make sure it returns the path unchanged or raises
`ValueError` for a path it does not know, and that it keeps no state that
changes its answer. Done when the build passes with the listing on. No check
enforces the second point.

## Review what changed without an edit

- **Reference section on every page.** The sidebar of every page now ends with
  the Reference section when at least one file is listed, also on a site
  without `[[source_pages]]` tables.
- **New public addresses.** Each automatically listed file is published at a
  route derived from its path, such as `readme.md.html` for `README.md`.
  Moving or renaming the file changes its address.
- **Links on source pages.** On a registered page, a link to a tracked
  Markdown file that is listed automatically now opens that file's page. In
  4.0.0 it was a source link to the repository.
- **Built files.** Above 60 listed files, or with the page lock on, the build
  writes `reference.tree.js` and `reference.index.html` in the html root. A
  project that compares or publishes its generated file list adds them. A page
  of the project with the address `reference.index.html` then fails the build
  with `route collision`.
- **`site-build.json`.** It gains the key `reference_tree`, which names the two
  files or is `null`. Its `source_pages` also maps every automatic route to its
  file. A project script that reads `source_pages` as the list of registered
  pages now gets the automatic pages too; the registered routes are the ones
  that do not end in `.md.html`.
- **Asset URLs.** `base.css`, `chapter-reader.css`, `chapter-reader.js`,
  `filelinks.js` and `nav.js` changed, so their `?v=` query changes in every
  page that loads them. A project check that compares built pages with a
  baseline compares the URL path without the query.
- **Exported source links.** `publish` now marks each link it points at a
  published file with `data-repo-exported`, and `filelinks.js` leaves such a
  link alone. With a source remote, a link to an admitted file such as
  `tools/fit.py` stays a link to the published copy; in 4.0.0 the browser
  turned it into a GitHub address with a wrong `docs/html/` part. A project
  check that compares published pages byte for byte sees the new attribute.
- **No source remote.** With `gh_repo = ""`, source links keep their local
  paths, and HTTP previews do not rewrite them to GitHub. `publish` rewrites
  the source links of every generated page in the html root, not only the
  pages in `[publication] pages`. A link to a tracked file that is not
  admitted keeps its local path, which leads outside the bundle; see
  [tooling and ownership](../../../../rules/site/authoring.md#tooling-and-ownership).
- **All chapters and print.** On pages with slide faces, All chapters hides
  the faces until its Slides switch is on, and printing from All chapters
  follows the switch. A project that prints its pages with faces from All
  chapters turns the switch on first. One chapter, Two chapters and the new
  Presentation view always show the faces;
  [shared reading layout](../../../../rules/site/reader.md#shared-reading-layout)
  describes the view.
- **Raw HTML.** In automatically listed files, raw `<script>`, `<style>`,
  `<iframe>`, `<svg>` and similar tags show as text, and other tags lose event
  handlers and outside addresses. Registered pages are not filtered.

## Review slide faces

This step is optional. [Slide faces](../../../../rules/writing/pages.md#slide-faces)
no longer prescribe one arrangement of lead, visual, points and facts row.
Each face's layout follows the shape of its content, and the faces of a
project share a frame: label row, title, scope line, type roles and tones.

Existing faces still build and render as before. To apply the rule, review
each face and sort it into one of three groups, with the reason:

1. A face without a real visual, or on a chapter with nothing to show: redraw
   or remove it.
2. A face with a real visual whose layout is below the standard of the rule,
   or that repeats its neighbours' arrangement without the same shape of
   content: redesign it.
3. Any other face: keep it.

```bash
grep -rln '^<!-- slide -->' --include='*.md' docs/topics
```

Removing or redrawing a face changes the page, and a project may count its
faces in checks or lock pages by hash. Ask the owner first. Done when the
owner has the list with its groups, or has decided to skip the review.

## Adopt the page lock

This step is optional. A project that does not set `lock = true` publishes
the same bundle as before. [Page lock](../../../../rules/site/publication.md#page-lock)
has the setup, what is locked and the limits; read the limits with the owner
before adopting it. The lock is not access control: the encrypted files are
public, and anyone who has a password can read and pass on what it opens.

1. Install the optional dependency wherever `publish` runs, in the hosted
   workflow too:

   ```bash
   python -m pip install -r .docs-kit/requirements-lock.txt
   ```

2. Set `lock = true` in the `[publication]` table of `docs/site/site.toml`.
3. Create two passwords and store them as repository secrets named
   `DOCSITE_GENERAL_PASSWORD` and `DOCSITE_REFERENCE_PASSWORD`. The general
   password opens the topic pages; the reference password opens everything,
   the Reference pages and exported Markdown files included. The rule says
   which passwords `publish` refuses and how to generate them.
4. Pass the two secrets only to the step that runs `publish`, as the rule's
   example shows, not to the whole job.
5. Deploy the `--out` directory of `publish`. The build output under
   `.build/docs/` stays plain: a workflow that deploys it, or uploads it as an
   artifact, publishes every page unlocked.
6. Keep the repository, its Actions logs and its workflow artifacts private.
   Whoever can change the workflow or the published site can replace the
   unlock script.
7. Run `publish` and read its summary: how many files each password opens,
   how many files stay readable, by type, and how many Reference pages are
   still linked from pages that the general password opens. Such links keep
   their text and address visible to every reader with the general password.
   Check the readable files for data that should not be public.

Done when a locked publish passes and the owner has read the summary. To
check the lock without the hosted workflow, set the two variables in the
shell and run `publish` into a new folder outside the project.

## Adopt the capability map

This step is optional. A project that does not set `tooling_roots` is not
checked and sees no change. [Name the need first](../../../../rules/engineering/code.md#name-the-need-first)
says why the map exists, and [the capability map](../../../../rules/engineering/code.md#the-capability-map)
owns its format and the check.

1. Copy the starter's empty map and link it from `docs/index.md`:

   ```bash
   cp .docs-kit/examples/starter/docs/CAPABILITY_MAP.md.tmpl docs/CAPABILITY_MAP.md
   ```

2. Write one row for each need that the code directly under the tooling
   folders meets, each need worded without naming an experiment, with a link
   to its code and its state. Leave the Imported by cells empty.
3. Add the settings above the first `[[nav]]` table of `docs/site/site.toml`,
   as [capability map settings](../../../../rules/site/authoring.md#capability-map-settings)
   shows, with the project's own folders.
4. Fill the generated column, then lint:

   ```bash
   python .docs-kit/docsite.py capability-map --project .
   python .docs-kit/docsite.py lint --project . --strict
   ```

5. Add the starter's route "Building tooling, a harness or other supporting
   code" to `AGENTS.md`, as the conformance check's router item asks.

Lint lists each file or folder under a tooling root that no row links. A
warning for a tool that imports from an experiment folder names code to move
into the tooling tree; moving it is a refactor for the owner to schedule, not
part of the upgrade. Route each such finding through `OPEN.md`, and leave
`experiment_roots` unset until the owner decides, so that strict lint passes.
Done when strict lint passes with `tooling_roots` set and the owner has the
list of findings.

## Reread pages that explain changed guides

These kit guides changed since 4.0.0. Reread the project pages that link to
them, as the conformance check asks, and update each explanation in the page's
own words:

- [Site authoring](../../../../rules/site/authoring.md): no source remote;
  the Reference section and its tree above 60 files; automatic reference
  listing.
- [Publication](../../../../rules/site/publication.md): private source pages
  refused; pages without a remote; page lock.
- [Reader](../../../../rules/site/reader.md): Presentation view; the Slides
  switch of All chapters.
- [Resources](../../../../rules/site/resources.md): the path adapter is asked
  once per run.
- [Page design and slide faces](../../../../rules/writing/pages.md): no
  prescribed arrangement.
- [Code and repository practices](../../../../rules/engineering/code.md):
  where code lives, name the need first, the capability map.
- [Experiment workflow](../../../../rules/experiments/workflow.md): the
  running total of each experiment and the step-back review.
- [Project conformance check](../../../../rules/conformance.md): the new
  capability map item.

The starter router `examples/starter/AGENTS.md.tmpl` gains one row, "Building
tooling, a harness or other supporting code", which reads the capability map
first. Add it to the project's `AGENTS.md` when the project keeps tooling.

## Land the upgrade

Commit the moved pin together with the settings and adaptations above, record
the old and new kit commits, the approved Reference list and the checks in the
project's worklog, and report the conformance findings with the owner's open
decisions. Push only after the [first step](#settle-what-the-reference-section-lists)
is done. [Pin and upgrade](../../../../README.md#pin-and-upgrade) has the
commands.
