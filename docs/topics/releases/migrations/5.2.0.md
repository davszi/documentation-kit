# Migrate to kit 5.2.0

This guide applies the [5.2.0 release notes](../releases.md#520--figures-in-a-dark-and-a-light-theme-and-checks-before-a-push)
to an existing 5.1.0 consumer. Prepare the upgrade as in the
[1.1.0 guide](1.1.0.md#prepare-the-deliverable): record the old and new kit
commits, keep a baseline build and follow the project's permissions and staging
workflow.

A project on an older version follows the earlier guides first, oldest first,
for their content steps, and then this one. It moves its pin once, straight to
`v5.2.0`.

## Move the pin

Follow [Move the pin](5.0.0.md#move-the-pin) in the 5.0.0 guide with the tag
`v5.2.0`. `requirements.txt` is unchanged.

## Give untracked tooling a row

Strict lint now warns when a file or folder directly under a tooling root is
not tracked yet and no row of the capability map links it, and when an
untracked file's imports change the Imported by column. Up to 5.1.0 lint
passed in both states and failed once the file was committed.

For a missing row, add the row, or move the file out of the tooling root, or
have Git ignore it. For a changing column, track the file with `git add` and
run `python .docs-kit/docsite.py capability-map --project .`. Done when
strict lint passes before the commit.

## Switch on the pre-push gate

Optional; the project's owner decides, and each clone switches it on for
itself. [One command and a pre-push gate](../../../../rules/site/validation.md#one-command-and-a-pre-push-gate)
has the rule.

1. Declare the project's own checks that its workflow runs, in
   `docs/site/site.toml` above the first `[[nav]]` table:

   ```toml
   [[checks]]
   name = "public paths"
   command = ["{python}", "-m", "unittest", "docs/site/checks/test_public_paths.py"]
   ```

2. Run `python .docs-kit/docsite.py check --project .` once and note how long
   it takes; every push will take that long.
3. Switch the gate on in the clone:

   ```bash
   git config core.hooksPath .docs-kit/hooks
   ```

   A project with hooks of its own copies `.docs-kit/hooks/pre-push` into its
   hooks folder instead.
4. Name the gate in the project's context record, so that a new clone or
   worktree switches it on too.

Done when `check` passes and a push runs it. No check enforces this step.

## Write generated figures in both themes

From 5.2.0 a generated figure file is written twice: `<name>.<ext>` in the
dark theme, which the page shows, and `<name>.light.<ext>` beside it, for
slides and print. [Generated figures](../../../../rules/site/authoring.md#generated-figures)
has the rule and the helper. Pages do not change: they keep showing
`<name>.<ext>`.

For each generator that writes figure files:

1. Put the drawing into a function that takes the colours, and write through
   the helper:

   ```python
   import sys; sys.path.insert(0, ".docs-kit/tooling")
   from figure_themes import write_both

   def draw(colors):
       fig, ax = plt.subplots()
       ax.plot(x, y, color=colors.accent)
       return fig

   write_both("docs/figures/speed.svg", draw)
   ```

   For a generator that builds SVG text, `draw` returns the text and passes
   the colours on to the helpers of `svg_figures.py`, such as
   `text(…, fill=colors.ink)`.
2. Delete colours the generator set by hand: hex values, `facecolor`,
   `style.use` and its own colour cycle. Take every colour from `colors`.
   A plot with more than four series folds the rest into one, or splits into
   several plots; it does not invent a fifth colour.
3. Add the light files to the generator's manifest, with the same script as
   their dark files, and to its `--check`; track or ignore them as the
   project does for the dark files. Lint then counts a light file in
   `docs/figures/` as kept, not as referenced by no page.
4. Look at both files once. A label placed for a dark background can vanish
   on white when its colour was set by hand.

A fragment with inline SVG that a page includes stays dark and gets no light
file; neither does a hand-drawn figure.

A project with many generators converts first the ones whose figures it needs
in slides, and lists the others in its open work. Done when each converted
generator writes both files and its check covers both, and the open work
names every generator that is not converted. No lint check enforces this
step.

## Land the upgrade

Run the [project conformance check](../../../../rules/conformance.md) and
report its findings. Then follow [Land the upgrade](5.0.0.md#land-the-upgrade)
in the 5.0.0 guide.
