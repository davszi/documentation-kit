# Migrate to kit 1.1.0

This guide applies the [1.1.0 release notes](../releases.md#110--focused-engineering-and-documentation-guides)
to an existing consumer. The release adds compatible routes and optional
configuration; project layout migration is a separate, optional part of adoption.
The [1.0.0 instructions](../releases.md#migrating-to-100) retain their historical
upgrade recipe. Follow the current project's permissions and staging workflow.
After the upgrade, run the [project conformance check](../../../../rules/conformance.md).

## Prepare the deliverable

Record the old kit commit, the intended new commit, the consumer source state
and its applicable checks. Preserve a baseline build and the page/content/media
identities needed to explain the comparison. Protect unrelated edits and active
jobs; use isolated staging or a worktree when shared-checkout ownership cannot
be established. Follow [shared Git practices](../../../../rules/engineering/git.md).

Review the changed shared contracts and map each local supplement to its owner
before replacing copied prose. Remove a copied shared rule only after its
unique project choices, commands, thresholds, prerequisites and evidence
requirements have a linked project home. Follow the project's deletion and
review gates; an upgrade does not authorize unrelated removals.

## Route contributors to the focused owners

- Use the [engineering guides](../../../../README.md#focused-guides) for code,
  performance, execution, delivery, handoffs and Git. Route Git work to the
  [commit-message](../../../../rules/engineering/git.md#commit-messages) and
  [shared-staging](../../../../rules/engineering/git.md#sharing-a-checkout) rules:
  messages require an explanatory body, and staging/landing needs one owner.
- Use one action-triggered [agent router](../../../../rules/documentation.md#agent-entrypoints-import-versus-point).
  Claude imports that router with a bare `@AGENTS.md`; the router names the
  project context, focused guides and task-specific prerequisites.
- Keep `rules/writing.md` and `rules/maintenance.md` as compatible entrypoints,
  or link directly to their focused guides; 3.0.0 removes their section anchors,
  so links to a section must then name the focused guide. Review the
  [page/figure ordering](../../../../rules/writing/pages.md#page-design),
  [representation guidance](../../../../rules/writing/figures.md#figures-and-comparisons)
  and [evidence scope](../../../../rules/records.md#numbers-and-staleness)
  when adapting local writing rules.

The revised starter uses `docs/PROJECT_CONTEXT.md` for orientation and
`docs/index.md` for reading routes. It demonstrates the current canonical roles;
it does not require an existing consumer to rename its project-owned files.

## Optional project layout migration

When the project chooses to replace a former `docs/project/` grouping, this
mapping separates reading routes from detailed owners. Create only homes the
project needs; retain domain-specific names and accepted local destinations.

| Former project home | Suggested current home or split |
|---|---|
| `docs/project/PROJECT_CONTEXT.md` | `docs/PROJECT_CONTEXT.md` for orientation |
| `docs/project/documentation.md` | `docs/index.md` for destinations and reading routes; detailed evidence preservation with its owner |
| `docs/project/conventions.md` | `docs/development/index.md` router plus focused project code/execution/runtime guides |
| `docs/project/<runtime>-development.md` | `docs/development/<runtime>.md` and focused children when needed |
| `docs/project/writing-docs.md` | `docs/site/writing.md` for project-specific writing and figures |
| `docs/project/evidence-locations.json` | `docs/evidence/locations.json`, retaining the project's schema |
| `docs/project/local-artifacts.json` and `local-artifacts.md` | `docs/evidence/` for cross-topic capture inventory and publication notes |
| `docs/project/sessions/` | `docs/sessions/` for dated assignments and recovery state |
| `docs/worklog.md` | Keep its existing canonical chronology; no move is required |

Update live task routes, relative links, configuration and supported historical
aliases together. Preserve public anchors, source-only notes and detailed
guides when introducing routers. A path move is not a reason to shorten an
owning contract or change readiness, acceptance or runtime settings.

Apply the [frozen-record rules](../../../../rules/records.md#evidence-identity-and-frozen-records):
retain exact evidence bytes, original logical origins, revisions, hashes and
required reference closure. Move a manifest without rewriting its historical
records. Keep append-only worklog entries and original dates intact. Historical
resolution belongs to explicit project aliases/adapters; current missing
targets remain errors. Relocation grants no permission to rerun old procedures.

## Adapt optional inventory and snapshot hooks

For a moved local-media inventory, set `local_artifacts_manifest` in
`docs/site/site.toml` to its project-relative file. The
[resource contract](../../../../rules/site/resources.md#resource-closure-and-evidence)
defaults to `docs/evidence/local-artifacts.json`; an omitted setting falls back
to `docs/project/local-artifacts.json` when needed (2.0.0 removes this fallback;
see the [2.0.0 migration guide](2.0.0.md)). An explicitly configured
missing file fails. No inventory is required when neither default exists and
the setting is omitted. Keep the existing schema and local-capture treatment.

An existing `evidence_validator` may additionally export
`document_origin(path, *, root)`. Add it only for registered exact source
snapshots whose saved link origin differs from their current location. Return
`None` for normal manifest/current-file handling. The project verifies the
snapshot's pins and registered origin before returning it; the kit validates
repository containment and rejects symlink paths. Keep negative checks for
changed pins, invalid origins and missing targets. Links, anchors and snippets
remain checked; the hook neither skips lint nor qualifies historical execution.
Existing adapters can omit the hook without changing their signatures.

## Validate, land and retain recovery

1. Select the exact reviewed kit commit and the project's tested environment.
   Inspect the complete proposed pointer and adaptation diff, including moves,
   deletions, manifest identity and any unrelated staged intent.
2. Run shared regression checks and the consumer's build, freshness, lint,
   evidence and other required checks. Compare source/content/media identities
   and generated output with the retained baseline; explain every intended
   difference. Preserved hashes alone do not prove a rendered layout.
3. Inspect actual wide/narrow output and paired columns where applicable,
   including controls, visible media and no-JavaScript/print requirements.
   Record checks actually run, failed attempts, skips and remaining gaps. Kit
   starter checks do not establish a consumer's adoption or deployment.
4. Land the exact kit pointer, related adaptations and consumer worklog entry
   in one reviewed deliverable. Record version, commit, comparisons and scoped
   results in the consumer's owning records. Pushing and publication retain
   their separate authorization gates.

Keep the former kit pin and matching consumer adaptations recoverable. If the
upgrade needs rollback, restore that coherent deliverable through the project's
reviewed Git workflow, rebuild and verify it. Preserve unrelated edits, saved
evidence and other contributors' history; do not restore old files over newer
pending work. The shared [history rules](../../../../rules/engineering/git.md#history-and-recovery)
and [publication gate](../../../../rules/site/publication.md#publishing-gate)
still apply.
